# 4. Infrastructure: the tools

Infrastructure is the layer that talks to the outside world: the SQL Server database (through EF Core) and the security tools (password hashing and JWT tokens). Application only defines interfaces such as `ITicketRepository`, `IAuthService` and `ITokenService`. Infrastructure writes the classes that implement them. This is **dependency inversion**: the business logic depends on an interface it owns, and the database code plugs in from outside. If we swapped SQL Server for something else, only this project would change.

**What it is:** The project file. It says which .NET version we target, which libraries we use, and which project we reference.


**Line by line:**
- `TargetFramework net10.0`: we build for .NET 10.
- `ImplicitUsings`: common namespaces like `System` and `System.Linq` are imported automatically, so files stay short.
- `Nullable enable`: the compiler warns when something might be null. That is why entities use `= null!` and `string?`.
- `FrameworkReference Microsoft.AspNetCore.App`: a class library does not get ASP.NET Core by default. This line gives it the shared framework, which contains `IConfiguration`, `IServiceCollection` and `PasswordHasher<T>`. It is used by the seeder and also by `AuthService` and `DependencyInjection.cs` (the comment only mentions the seeder).
- `Microsoft.EntityFrameworkCore.SqlServer`: the EF Core provider that turns LINQ into SQL Server SQL. `EntityFrameworkCore`, `.Relational` and `.Abstractions` are also listed by name.
- `.Design` and `.Tools` with `PrivateAssets all`: needed only at design time for `Add-Migration` and `Update-Database` in Package Manager Console. `PrivateAssets all` means they do not flow to the API project as a runtime dependency.
- `Microsoft.IdentityModel.JsonWebTokens 8.19.2`: gives us `JsonWebTokenHandler` to create tokens. The version matches the one `JwtBearer` 10.0.13 uses in the API, so both sides use the same library.
- `System.Security.Cryptography.Pkcs`: no code in this project uses it. It is a **security pin**. The SQL Server driver depends on an older Pkcs (9.0.11) that has two published vulnerabilities. Naming the package directly makes NuGet use 10.0.13 instead, because a direct reference wins over a transitive one. We tested it on Nov 16: removing the line brings back 8 `NU1903`/`NU1902` "known vulnerability" warnings.

**Committee might ask: "Why is there a package nobody uses?"** It isn't for our code. It overrides a vulnerable version that EF Core's SQL Server driver would otherwise bring in. `dotnet list package --vulnerable --include-transitive` shows no vulnerable packages with it, and a high-severity one without it.
- `ProjectReference` to Application only: Infrastructure points inward to Application (and through it to Domain). Nothing points back at Infrastructure, except the API, which wires it up.

Note: `.Relational` and `.Abstractions` already come in through `.SqlServer`, so listing them is not strictly needed. It does no harm. CLAUDE.md says to keep `.Abstractions` in Domain on purpose.

**Committee might ask:**
- *Why does a class library reference ASP.NET Core?* It needs `PasswordHasher<T>`, `IConfiguration` and `IServiceCollection`, which live in the ASP.NET Core shared framework. A `FrameworkReference` is the official way to get them without pulling single NuGet packages.

## [DependencyInjection.cs](../../TicketingSystem.Infrastructure/DependencyInjection.cs)

**What it is:** One extension method, `AddInfrastructure`, that registers every Infrastructure class in the dependency injection (DI) container. `Program.cs` calls it in one line.

**The code:**

```csharp
using Microsoft.AspNetCore.Identity;
using Microsoft.EntityFrameworkCore;
using Microsoft.Extensions.Configuration;
using Microsoft.Extensions.DependencyInjection;
using TicketingSystem.Application.Interfaces;
using TicketingSystem.Domain.Entities;
using TicketingSystem.Infrastructure.Auth;
using TicketingSystem.Infrastructure.Persistence;
using TicketingSystem.Infrastructure.Persistence.Repositories;

namespace TicketingSystem.Infrastructure
{
    // Everything Infrastructure needs registered lives here, so Program.cs stays one line:
    // builder.Services.AddInfrastructure(builder.Configuration);
    public static class DependencyInjection
    {
        public static IServiceCollection AddInfrastructure(this IServiceCollection services, IConfiguration configuration)
        {
            var connectionString = configuration.GetConnectionString("Default")
                ?? throw new InvalidOperationException("Connection string 'Default' is missing in appsettings.json.");

            services.AddDbContext<AppDbContext>(options => options.UseSqlServer(connectionString));

            services.AddSingleton(JwtOptions.Load(configuration));
            services.AddSingleton<IPasswordHasher<User>, PasswordHasher<User>>();
            services.AddSingleton<ITokenService, JwtTokenService>();
            services.AddScoped<IAuthService, AuthService>(); // Scoped because it uses the scoped DbContext
            services.AddScoped<ITicketRepository, TicketRepository>();
            services.AddScoped<IUserRepository, UserRepository>();
            services.AddScoped<ITeamRepository, TeamRepository>();

            return services;
        }
    }
}
```

**Line by line:**
- Line 17, `this IServiceCollection services`: `IServiceCollection` is the list of "when someone asks for X, give them Y" rules that ASP.NET Core builds at startup. The `this` keyword makes it an extension method, so we can write `builder.Services.AddInfrastructure(...)`.
- Lines 19-20: reads `ConnectionStrings:Default` from `appsettings.json` (the LocalDB `MizanDb` string). If it is missing, the app stops at startup with a clear message instead of failing on the first query.
- Line 22, `AddDbContext<AppDbContext>(... UseSqlServer ...)`: registers our DbContext and tells EF to use SQL Server. `AddDbContext` registers it as **scoped**: one new `AppDbContext` per HTTP request, thrown away at the end. That keeps each request's change tracker separate.
- Line 24, `AddSingleton(JwtOptions.Load(configuration))`: loads and validates the JWT settings once and shares the same object everywhere. A **singleton** is one instance for the whole app life.
- Line 25: the password hasher has no state, so one shared instance is fine. We register it against the interface `IPasswordHasher<User>` so `AuthService` asks for the interface.
- Line 26: `JwtTokenService` only depends on `JwtOptions` (also a singleton), so it can be a singleton too.
- Line 27, `AddScoped<IAuthService, AuthService>`: **scoped** means one instance per request. `AuthService` uses the DbContext, which is scoped. A singleton must never hold a scoped service, because it would keep one DbContext alive for all requests.
- Lines 28-30: the three repositories. Each one uses the DbContext, so they are scoped too. Because they share the same scope, the `TicketRepository` and `UserRepository` in one request share the same `AppDbContext`.
- The left side is always an **Application interface**; the right side is the Infrastructure class. This line is where dependency inversion happens.

**Committee might ask:**
- *Why scoped and not singleton for repositories?* `DbContext` is not thread-safe and keeps a change tracker. One per request keeps requests isolated. A singleton repository would share one DbContext across all users at once.
- *Why put this in Infrastructure and not Program.cs?* The API should not know the concrete classes. It just calls `AddInfrastructure`. Adding a repository changes only this file.

## [AppDbContext.cs](../../TicketingSystem.Infrastructure/Persistence/AppDbContext.cs)

**What it is:** Our EF Core `DbContext`: the object that represents one working session with the database. It knows the tables, tracks loaded entities, and writes changes back with `SaveChangesAsync`.

**The code:**

```csharp
using Microsoft.EntityFrameworkCore;
using TicketingSystem.Domain.Entities;

namespace TicketingSystem.Infrastructure.Persistence
{
    public class AppDbContext : DbContext
    {
        public AppDbContext(DbContextOptions<AppDbContext> options) : base(options) { }

        // One DbSet per table
        public DbSet<User> Users => Set<User>();
        public DbSet<Team> Teams => Set<Team>();
        public DbSet<TeamMember> TeamMembers => Set<TeamMember>();
        public DbSet<Ticket> Tickets => Set<Ticket>();
        public DbSet<TicketAssignment> TicketAssignments => Set<TicketAssignment>();
        public DbSet<CodeSnapshot> CodeSnapshots => Set<CodeSnapshot>();
        public DbSet<TicketResponse> TicketResponses => Set<TicketResponse>();
        public DbSet<Comment> Comments => Set<Comment>();
        public DbSet<AuditLog> AuditLogs => Set<AuditLog>();

        protected override void OnModelCreating(ModelBuilder modelBuilder)
        {
            base.OnModelCreating(modelBuilder);

            // Finds every IEntityTypeConfiguration<T> class in this project (the
            // Configurations folder) and applies it, so we don't register them one by one
            modelBuilder.ApplyConfigurationsFromAssembly(typeof(AppDbContext).Assembly);
        }

        // Runs on every save: stamps UpdatedAt automatically so no service has to remember it
        public override Task<int> SaveChangesAsync(CancellationToken cancellationToken = default)
        {
            foreach (var entry in ChangeTracker.Entries<BaseEntity>())
            {
                if (entry.State == EntityState.Modified)
                    entry.Entity.UpdatedAt = DateTime.UtcNow;
            }

            return base.SaveChangesAsync(cancellationToken);
        }
    }
}
```

**Line by line:**
- Line 6, `: DbContext`: we inherit EF Core's base class, which does the real work (queries, change tracking, saving).
- Line 8, the constructor: takes `DbContextOptions<AppDbContext>`. Those options (SQL Server + connection string) come from `AddDbContext` in `DependencyInjection.cs`. The context itself does not know the connection string.
- Lines 11-19, `DbSet<T>`: a `DbSet` is a table you can query with LINQ (`db.Tickets.Where(...)`) and add rows to (`db.Tickets.Add(...)`). `=> Set<User>()` is a read-only property that asks EF for the set. This style avoids nullable warnings that `{ get; set; }` would cause.
- **LINQ to SQL:** when you write `db.Tickets.Where(t => t.ClientId == id).ToListAsync()`, nothing runs until `ToListAsync`. Then EF translates the whole chain into one SQL `SELECT ... WHERE ClientId = @p0` and sends it to SQL Server.
- Line 21, `OnModelCreating`: EF calls this once to build its "model" (which tables, columns, keys and relationships exist).
- Line 27, `ApplyConfigurationsFromAssembly`: scans this project's assembly for every class that implements `IEntityTypeConfiguration<T>` (the 9 files in `Configurations/`) and runs them. Adding a new configuration file needs no change here.
- Line 31, `override SaveChangesAsync`: we hook into every save. All services save through this method, so the rule below cannot be forgotten.
- Line 33, `ChangeTracker.Entries<BaseEntity>()`: the **change tracker** is EF's memory of every entity it loaded or was told to add, and its state (`Added`, `Modified`, `Deleted`, `Unchanged`). `Entries<BaseEntity>()` lists only entities that inherit `BaseEntity`. `AuditLog` is not a `BaseEntity`, so it is skipped (it is never updated anyway).
- Lines 35-36: only `Modified` rows get a new `UpdatedAt`. New rows (`Added`) keep `UpdatedAt` as null; their `CreatedAt` is already set in `BaseEntity`. We use `UtcNow` so time zones never mix.
- Line 39: then the real EF save runs.

Note: only the async `SaveChangesAsync(CancellationToken)` is overridden. The sync `SaveChanges()` would not stamp `UpdatedAt`. The project uses async everywhere, so this is fine today.

**Committee might ask:**
- *Why stamp UpdatedAt here and not in each service?* One place, so no service can forget. It is a technical detail, not business logic.
- *What is the DbContext's lifetime?* Scoped: one per HTTP request. It is created when the request needs it and disposed at the end.
- *How does the database get created?* From migrations. `Add-Migration` compares this model with the last snapshot and writes C# that creates or changes tables. `Update-Database` runs it. We have one migration, `InitialCreate`, in `Persistence/Migrations`.

## Configurations: shared ideas

All 9 files in `Persistence/Configurations/` follow the same pattern. Some concepts first, so the files below are easy to read.

- **`IEntityTypeConfiguration<T>`**: an interface with one method, `Configure(EntityTypeBuilder<T> builder)`. It holds the database rules for one entity. This keeps the Domain entities clean (no database attributes) and keeps `AppDbContext` short.
- **Fluent API**: the chained calls like `builder.Property(...).HasMaxLength(100).IsRequired()`. It is EF's code way of describing columns, keys and relationships.
- **Conventions**: anything we do not configure, EF guesses. A property named `Id` becomes the primary key. A `Guid TicketId` next to a `Ticket` navigation becomes a foreign key. Table names come from the `DbSet` names.
- **`HasMaxLength(n)`**: the column becomes `nvarchar(n)` instead of `nvarchar(max)`. It protects the database from huge inputs and lets SQL Server index the column (you cannot index `nvarchar(max)`).
- **`IsRequired()`**: the column becomes `NOT NULL`.
- **`HasConversion<string>()`**: stores an enum as its name (`"TeamLeader"`) instead of its number (`2`). The data is readable in SSMS, and reordering the enum in C# later cannot silently change the meaning of old rows. The `HasMaxLength` after it sizes that text column.
- **`HasOne(...).WithMany(...).HasForeignKey(...)`**: describes a relationship. "A ticket has one Client; a user has many tickets (no collection on User); the key is `ClientId`." `WithMany()` with no argument means the other side has no collection property.
- **`OnDelete(DeleteBehavior.Restrict)`**: if a row is still referenced, the database refuses to delete it. The default for required relationships would be cascade (delete the children too). We use Restrict everywhere for two reasons: SQL Server refuses "multiple cascade paths" (many FKs point to `Users`), and we soft-delete (`IsDeleted`) anyway, so real deletes should not happen.
- **`HasIndex(...)`**: creates a database index so searching by that column is fast. **`.IsUnique()`** also makes the database reject duplicates. That is a safety net even if the C# code has a bug.

## [UserConfiguration.cs](../../TicketingSystem.Infrastructure/Persistence/Configurations/UserConfiguration.cs)

**What it is:** Rules for the `Users` table.

**The code:**

```csharp
using Microsoft.EntityFrameworkCore;
using Microsoft.EntityFrameworkCore.Metadata.Builders;
using TicketingSystem.Domain.Entities;

namespace TicketingSystem.Infrastructure.Persistence.Configurations
{
    public class UserConfiguration : IEntityTypeConfiguration<User>
    {
        public void Configure(EntityTypeBuilder<User> builder)
        {
            builder.Property(u => u.Name).HasMaxLength(100).IsRequired();
            builder.Property(u => u.Email).HasMaxLength(256).IsRequired();
            builder.Property(u => u.PasswordHash).IsRequired();

            // Store the enum as text ("TeamLeader") instead of a number (2): readable in SSMS
            builder.Property(u => u.Role).HasConversion<string>().HasMaxLength(30);

            // No two users with the same email (it's the login)
            builder.HasIndex(u => u.Email).IsUnique();
        }
    }
}
```

**Line by line:**
- Line 7: implements `IEntityTypeConfiguration<User>`, so `ApplyConfigurationsFromAssembly` finds it.
- Lines 11-12: name up to 100 characters, email up to 256 (the common maximum for an email address). Both required.
- Line 13: `PasswordHash` is required but has no max length, so it is `nvarchar(max)`. The hash is a fixed-size Base64 string; we never search by it, so no index is needed.
- Line 16: `Role` stored as text, up to 30 characters (`"TeamsManager"` is the longest).
- Line 19: unique index on `Email`. Email is the login name, so two accounts with the same email must be impossible. The index also makes the login query fast.

Note: with SQL Server's default (case-insensitive) collation, `Ali@x.com` and `ali@x.com` count as the same email for both the unique index and the login query.

## [TeamConfiguration.cs](../../TicketingSystem.Infrastructure/Persistence/Configurations/TeamConfiguration.cs) and [TeamMemberConfiguration.cs](../../TicketingSystem.Infrastructure/Persistence/Configurations/TeamMemberConfiguration.cs)

**What it is:** Rules for teams and for the join table that links users to teams.

**The code (TeamConfiguration.cs):**

```csharp
using Microsoft.EntityFrameworkCore;
using Microsoft.EntityFrameworkCore.Metadata.Builders;
using TicketingSystem.Domain.Entities;

namespace TicketingSystem.Infrastructure.Persistence.Configurations
{
    public class TeamConfiguration : IEntityTypeConfiguration<Team>
    {
        public void Configure(EntityTypeBuilder<Team> builder)
        {
            builder.Property(t => t.Name).HasMaxLength(100).IsRequired();
            builder.HasIndex(t => t.Name).IsUnique();

            // Restrict = deleting a user who leads a team is blocked by the database.
            // We use Restrict everywhere: SQL Server refuses "multiple cascade paths"
            // (several FKs pointing at Users), and we soft-delete anyway.
            builder.HasOne(t => t.Leader)
                   .WithMany()
                   .HasForeignKey(t => t.LeaderId)
                   .OnDelete(DeleteBehavior.Restrict);
        }
    }
}
```

**The code (TeamMemberConfiguration.cs):**

```csharp
using Microsoft.EntityFrameworkCore;
using Microsoft.EntityFrameworkCore.Metadata.Builders;
using TicketingSystem.Domain.Entities;

namespace TicketingSystem.Infrastructure.Persistence.Configurations
{
    public class TeamMemberConfiguration : IEntityTypeConfiguration<TeamMember>
    {
        public void Configure(EntityTypeBuilder<TeamMember> builder)
        {
            builder.HasOne(m => m.Team)
                   .WithMany(t => t.Members)
                   .HasForeignKey(m => m.TeamId)
                   .OnDelete(DeleteBehavior.Restrict);

            builder.HasOne(m => m.User)
                   .WithMany()
                   .HasForeignKey(m => m.UserId)
                   .OnDelete(DeleteBehavior.Restrict);

            // A user can be in a given team only once
            builder.HasIndex(m => new { m.TeamId, m.UserId }).IsUnique();
        }
    }
}
```

**Line by line:**
- TeamConfiguration lines 11-12: team names are required, up to 100 characters, and unique.
- TeamConfiguration lines 17-20: a team has one `Leader` (a `User`). `WithMany()` is empty because `User` has no "teams I lead" collection. `Restrict`: you cannot delete a user who still leads a team. The comment explains why Restrict is used everywhere.
- TeamMemberConfiguration lines 11-14: `WithMany(t => t.Members)` links this side to the `Team.Members` collection, so EF knows `team.Members` and `TeamMember.Team` are the same relationship.
- Lines 16-19: the link to the user. No collection on `User`.
- Line 22, `HasIndex(m => new { m.TeamId, m.UserId }).IsUnique()`: a **composite** unique index over two columns. The same user cannot be added to the same team twice. The same user *can* be in two different teams.

## [TicketConfiguration.cs](../../TicketingSystem.Infrastructure/Persistence/Configurations/TicketConfiguration.cs)

**What it is:** Rules for the most important table, `Tickets`. It includes the concurrency token.

**The code:**

```csharp
using Microsoft.EntityFrameworkCore;
using Microsoft.EntityFrameworkCore.Metadata.Builders;
using TicketingSystem.Domain.Entities;

namespace TicketingSystem.Infrastructure.Persistence.Configurations
{
    public class TicketConfiguration : IEntityTypeConfiguration<Ticket>
    {
        public void Configure(EntityTypeBuilder<Ticket> builder)
        {
            builder.Property(t => t.Title).HasMaxLength(200).IsRequired();
            builder.Property(t => t.Description).HasMaxLength(4000).IsRequired();
            builder.Property(t => t.RepositoryUrl).HasMaxLength(500).IsRequired();

            builder.Property(t => t.Status).HasConversion<string>().HasMaxLength(30);
            builder.Property(t => t.Priority).HasConversion<string>().HasMaxLength(20);

            // Maps to SQL Server's rowversion type (auto-updated concurrency token)
            builder.Property(t => t.RowVersion).IsRowVersion();

            // Ticket has TWO foreign keys to Users (Client and Manager), so EF can't
            // guess which navigation goes with which key: we spell each one out.
            builder.HasOne(t => t.Client)
                   .WithMany()
                   .HasForeignKey(t => t.ClientId)
                   .OnDelete(DeleteBehavior.Restrict);

            builder.HasOne(t => t.Manager)
                   .WithMany()
                   .HasForeignKey(t => t.ManagerId)
                   .OnDelete(DeleteBehavior.Restrict);

            builder.HasOne(t => t.Team)
                   .WithMany()
                   .HasForeignKey(t => t.TeamId)
                   .OnDelete(DeleteBehavior.Restrict);

            // Indexes on the columns we filter by most (ticket lists per role)
            builder.HasIndex(t => t.Status);
            builder.HasIndex(t => t.ClientId);
            builder.HasIndex(t => t.TeamId);
            builder.HasIndex(t => t.CreatedAt);
        }
    }
}
```

**Line by line:**
- Lines 11-13: title 200, description 4000, repo URL 500 characters, all required. 4000 is the largest `nvarchar` size before SQL Server needs `nvarchar(max)`.
- Lines 15-16: `Status` and `Priority` are enums stored as text.
- Line 19, `IsRowVersion()`: maps `byte[] RowVersion` to SQL Server's `rowversion` type. SQL Server changes this value automatically every time the row is updated. EF also treats it as a **concurrency token**: every `UPDATE Tickets` it sends includes `WHERE Id = @id AND RowVersion = @oldValue`. If someone else saved the ticket after we loaded it, the value no longer matches, zero rows are updated, and EF throws `DbUpdateConcurrencyException`. This is **optimistic concurrency**: we do not lock the row while a user is working; we just detect the clash at save time.
- Lines 23-26 and 28-31: two FKs to the same `Users` table (`ClientId`, `ManagerId`). EF cannot guess which navigation goes with which key, so each one is written out. `ManagerId` is a `Guid?` in the entity, so that FK is nullable (no manager until routing).
- Lines 33-36: `TeamId` is also nullable (no team until routed). All three use `Restrict`.
- Lines 39-42: plain (non-unique) indexes on the columns the ticket lists filter and sort by: status, client (client's own list), team (leader's list) and creation date (newest first).

**Committee might ask:**
- *What happens if two leaders act on the same ticket at the same moment?* Both load the same RowVersion. The first save wins and SQL Server changes the RowVersion. The second save's `WHERE RowVersion = @old` matches nothing, EF throws, the repository turns it into `ConflictException`, and the API returns 409 "reload and try again".
- *Why optimistic and not a lock?* Conflicts are rare, and a lock would block other users while someone has the page open. Optimistic concurrency costs nothing until a real clash happens.

## [TicketAssignmentConfiguration.cs](../../TicketingSystem.Infrastructure/Persistence/Configurations/TicketAssignmentConfiguration.cs)

**What it is:** Rules for `TicketAssignments`: which member is assigned to which ticket, and who assigned them.

**The code:**

```csharp
using Microsoft.EntityFrameworkCore;
using Microsoft.EntityFrameworkCore.Metadata.Builders;
using TicketingSystem.Domain.Entities;

namespace TicketingSystem.Infrastructure.Persistence.Configurations
{
    public class TicketAssignmentConfiguration : IEntityTypeConfiguration<TicketAssignment>
    {
        public void Configure(EntityTypeBuilder<TicketAssignment> builder)
        {
            builder.HasOne(a => a.Ticket)
                   .WithMany(t => t.Assignments)
                   .HasForeignKey(a => a.TicketId)
                   .OnDelete(DeleteBehavior.Restrict);

            builder.HasOne(a => a.User)
                   .WithMany()
                   .HasForeignKey(a => a.UserId)
                   .OnDelete(DeleteBehavior.Restrict);

            builder.HasOne(a => a.AssignedBy)
                   .WithMany()
                   .HasForeignKey(a => a.AssignedById)
                   .OnDelete(DeleteBehavior.Restrict);

            // The same member can't be assigned to the same ticket twice
            builder.HasIndex(a => new { a.TicketId, a.UserId }).IsUnique();
        }
    }
}
```

**Line by line:**
- Lines 11-14: each assignment belongs to one ticket and appears in `Ticket.Assignments`.
- Lines 16-19 and 21-24: two FKs to `Users`: the assigned member (`UserId`) and the leader who assigned them (`AssignedById`). Two FKs to the same table, so cascade would be impossible anyway.
- Line 27, unique `(TicketId, UserId)`: a member can be assigned to a ticket only once. The workflow skips members who are already assigned, so this index is a safety net that should never fire in normal use. If two leaders assign the same member in the same millisecond, the second insert fails here.

Note: the unique index also counts soft-deleted assignments. That is fine today because assignments are never removed (see `docs/SESSION_NOTES_2026-11-08.md`).

- *An audit log without foreign keys? Isn't that bad design?* It is a deliberate trade-off. An audit log is a permanent record. It must never block a delete or be deleted with its parent. Integrity comes from the code: only the workflow writes these rows, inside the same save as the change they describe.

## [DbSeeder.cs](../../TicketingSystem.Infrastructure/Persistence/DbSeeder.cs)

**What it is:** Fills an empty database with demo data: one user per role (plus a second member) and the "Backend Team". It runs at startup, only in Development.

**The code:** (copied exactly, except the password value on line 13, which is replaced with a placeholder here. The real value is in the file; it is a demo-only password.)

```csharp
using Microsoft.AspNetCore.Identity;
using Microsoft.EntityFrameworkCore;
using TicketingSystem.Domain.Entities;
using TicketingSystem.Domain.Enums;

namespace TicketingSystem.Infrastructure.Persistence
{
    // Fills an empty database with demo data: one user per role and one team.
    // Runs at startup in Development only. Does nothing if users already exist.
    public static class DbSeeder
    {
        // DEV/DEMO ONLY. Every seeded account uses this password.
        private const string DemoPassword = "<demo password, see the file>";

        public static async Task SeedAsync(AppDbContext db)
        {
            if (await db.Users.AnyAsync())
                return;

            var hasher = new PasswordHasher<User>();

            User NewUser(string name, string email, UserRole role)
            {
                var user = new User { Name = name, Email = email, Role = role };
                // Never store the plain password: store a salted hash
                user.PasswordHash = hasher.HashPassword(user, DemoPassword);
                return user;
            }

            var admin   = NewUser("System Admin",   "admin@mizan.local",   UserRole.Admin);
            var manager = NewUser("Teams Manager",  "manager@mizan.local", UserRole.TeamsManager);
            var leader  = NewUser("Team Leader",    "leader@mizan.local",  UserRole.TeamLeader);
            var member1 = NewUser("Member One",     "member1@mizan.local", UserRole.TeamMember);
            var member2 = NewUser("Member Two",     "member2@mizan.local", UserRole.TeamMember);
            var client  = NewUser("Demo Client",    "client@mizan.local",  UserRole.Client);

            db.Users.AddRange(admin, manager, leader, member1, member2, client);

            var team = new Team { Name = "Backend Team", Leader = leader };
            team.Members.Add(new TeamMember { User = member1 });
            team.Members.Add(new TeamMember { User = member2 });
            db.Teams.Add(team);

            await db.SaveChangesAsync();
        }
    }
}
```

**Line by line:**
- Line 10, `static class`: no state, nothing to inject. `Program.cs` calls `DbSeeder.SeedAsync(db)` inside `if (app.Environment.IsDevelopment())`, using a DbContext from a temporary DI scope.
- Line 13: one shared demo password for all seeded accounts. It is a `const` in source code, which is acceptable only because these are throwaway demo accounts that never exist in production. Real users would set their own password.
- Lines 17-18, `AnyAsync()`: if any user exists, stop. This makes the seeder safe to run on every startup: it fills the database once and never duplicates data.
- Line 20, `new PasswordHasher<User>()`: `PasswordHasher<T>` is ASP.NET Core Identity's password tool. `HashPassword` creates a random **salt**, runs the password through PBKDF2 (a deliberately slow hash, many iterations), and returns one Base64 string that contains the algorithm version, salt and hash. `VerifyHashedPassword` later reads them back to check a login.
- Lines 22-28: a **local function** (a small function inside a method) that builds a user and hashes the password. The comment states the rule: never store the plain password.
- Lines 30-35: the six demo users. The `.local` domain is reserved, so these can never be real emails.
- Line 37, `AddRange`: marks all six users as `Added` in the change tracker. Nothing is sent to SQL yet.
- Lines 39-42: the team, with `Leader = leader` and two `TeamMember` rows. We set navigation properties, not ids. EF fills `LeaderId`, `TeamId` and `UserId` for us at save time.
- Line 44: one `SaveChangesAsync`, so all inserts go in one transaction. Either all demo data is created or none.

Note: here, adding members through `team.Members.Add(...)` is fine, because the whole team is new and `db.Teams.Add(team)` marks everything reachable from it as `Added`. The repositories avoid this style for children of an **existing, tracked** ticket (see `TicketRepository` below).

Note: the seeder creates its own `PasswordHasher<User>` instead of using the one registered in DI. Both use the same default settings, so the hashes are compatible.

**Committee might ask:**
- *Why a salted hash and not plain text or encryption?* A hash cannot be reversed. If the database leaks, attackers do not get passwords. The random salt means two users with the same password get different hashes, so precomputed "rainbow tables" do not work. Encryption would be worse: anyone with the key could decrypt every password.
- *Is a hardcoded password a security problem?* Only for these demo accounts, and the seeder runs only in Development and only on an empty database. In production there would be a registration or admin flow (future work).

## [TicketRepository.cs](../../TicketingSystem.Infrastructure/Persistence/Repositories/TicketRepository.cs)

**What it is:** The EF Core implementation of Application's `ITicketRepository`. Every ticket read and write in the app goes through here. Application never touches `AppDbContext` directly.

### Part 1: adding rows and saving

```csharp
using System.Linq.Expressions;
using Microsoft.EntityFrameworkCore;
using TicketingSystem.Application.Exceptions;
using TicketingSystem.Application.Interfaces;
using TicketingSystem.Domain.Entities;

namespace TicketingSystem.Infrastructure.Persistence.Repositories
{
    public class TicketRepository(AppDbContext db) : ITicketRepository
    {
        public void Add(Ticket ticket) => db.Tickets.Add(ticket);

        public void AddAuditLog(AuditLog entry) => db.AuditLogs.Add(entry);

        // EF also links each one into the loaded ticket's collection right away
        public void AddAssignment(TicketAssignment assignment) => db.TicketAssignments.Add(assignment);

        public void AddSnapshot(CodeSnapshot snapshot) => db.CodeSnapshots.Add(snapshot);

        public void AddResponse(TicketResponse response) => db.TicketResponses.Add(response);

        public async Task SaveChangesAsync(CancellationToken cancellationToken)
        {
            try
            {
                await db.SaveChangesAsync(cancellationToken);
            }
            catch (DbUpdateConcurrencyException)
            {
                // Ticket.RowVersion changed since we loaded it: someone else saved first.
                // Turned into an Application exception here, so the API doesn't need to know EF.
                throw new ConflictException("Someone else changed this ticket at the same time. Reload it and try again.");
            }
        }
```

**Line by line:**
- Line 9, `TicketRepository(AppDbContext db)`: a **primary constructor** (C# 12). `db` is available in every method. DI gives us the request's scoped `AppDbContext`.
- Line 11, `Add`: `db.Tickets.Add(ticket)` marks the new ticket as `Added`. Its Before snapshot and first audit row are added the same way by `TicketService`. Nothing hits the database until `SaveChangesAsync`.
- Line 13, `AddAuditLog`: same, for audit rows.
- Lines 16, 18, 20, `AddAssignment`, `AddSnapshot`, `AddResponse`: new child rows of an **existing** ticket are added to their own `DbSet`, not with `ticket.Assignments.Add(...)`. Why: our ids are set in C# (`Guid.NewGuid()` in `BaseEntity`). When EF finds a new object inside the collection of an already-tracked entity and that object already has a non-empty key, it assumes the row exists and marks it `Modified`. It then sends an `UPDATE` instead of an `INSERT`. The update affects zero rows, and EF reports a concurrency conflict. This bug was caught by the end-to-end tests and fixed this way. `DbSet.Add` always means `Added`, so we get an `INSERT`.
- Line 15, the comment: after `db.TicketAssignments.Add(...)`, EF's "fix-up" also puts the new row into the tracked ticket's `Assignments` collection, so the workflow code sees it straight away.
- Lines 22-34, `SaveChangesAsync`: calls our `AppDbContext.SaveChangesAsync` (which stamps `UpdatedAt`).
- Line 28, `catch (DbUpdateConcurrencyException)`: `DbUpdateConcurrencyException` is the EF exception for "an UPDATE or DELETE affected fewer rows than expected". In our model that means the ticket's `RowVersion` no longer matched.
- Line 32: we translate it into `ConflictException`, which lives in **Application**. `GlobalExceptionHandler` in the API maps `ConflictException` to **409 Conflict**. The API and Application never need to know EF exists.

Note: only `DbUpdateConcurrencyException` is translated. Other database errors (for example, the unique index on assignments) still surface as 500. This was a deliberate choice in the code review: turning every database error into 409 would hide real bugs.

### Part 2: list and details (read-only)

```csharp
        public async Task<IReadOnlyList<Ticket>> ListAsync(Expression<Func<Ticket, bool>> filter, CancellationToken cancellationToken)
        {
            return await db.Tickets
                .AsNoTracking()
                .Include(t => t.Client)
                .Include(t => t.Team)
                .Where(t => !t.IsDeleted) // Soft-delete query filters aren't set up, so excluded by hand
                .Where(filter)
                .OrderByDescending(t => t.CreatedAt)
                .ToListAsync(cancellationToken);
        }

        public Task<Ticket?> GetDetailsAsync(Guid ticketId, Expression<Func<Ticket, bool>> filter, CancellationToken cancellationToken)
        {
            return db.Tickets
                .AsNoTracking()
                .Include(t => t.Client)
                .Include(t => t.Manager)
                .Include(t => t.Team)
                .Include(t => t.Assignments.Where(a => !a.IsDeleted))
                    .ThenInclude(a => a.User)
                .Include(t => t.Snapshots.Where(s => !s.IsDeleted))
                .Include(t => t.Responses.Where(r => !r.IsDeleted))
                    .ThenInclude(r => r.Author)
                .AsSplitQuery() // Several collections in one JOIN would multiply the rows
                .Where(t => t.Id == ticketId && !t.IsDeleted)
                .Where(filter)
                .FirstOrDefaultAsync(cancellationToken);
        }
```

**Line by line:**
- Line 36, `Expression<Func<Ticket, bool>> filter`: the visibility rule from `TicketVisibility.VisibleTo(user)` in Application (for example `t => t.ClientId == userId` for a client). It is an `Expression`, not a plain `Func`, so EF can read it and translate it into SQL. A `Func` would force EF to load every ticket and filter in memory. This way the one visibility rule lives in Application, and Infrastructure just applies it.
- Line 39, `AsNoTracking()`: tells EF not to put the loaded entities into the change tracker. It is faster and uses less memory. We use it whenever we only read data to build a DTO.
- Lines 40-41, `Include(...)`: EF does not load related entities by default. `Include` adds a JOIN so `ticket.Client` and `ticket.Team` are filled (the list shows client name and team name).
- Line 42: `!t.IsDeleted`. EF global query filters for soft-delete are not set up (cut from MVP), so every query excludes deleted rows by hand.
- Line 43: the visibility filter. Both `Where` calls end up in the same SQL `WHERE`, joined with `AND`.
- Line 44: newest tickets first (uses the `CreatedAt` index).
- Line 45: `ToListAsync` is where the SQL actually runs.
- Lines 48-64, `GetDetailsAsync`: one ticket with everything the details page needs.
- Line 55, `Include(t => t.Assignments.Where(a => !a.IsDeleted))`: a **filtered include**. Only non-deleted assignments are loaded.
- Line 56, `ThenInclude(a => a.User)`: `ThenInclude` goes one level deeper: for each assignment, also load its user (to show member names).
- Lines 57-59: snapshots, and responses with their authors, again skipping soft-deleted rows.
- Line 60, `AsSplitQuery()`: with three collections, one big JOIN would return (assignments × snapshots × responses) rows, a "cartesian explosion". Split query sends one SQL query per collection instead and stitches the results together.
- Line 61: match the id and skip deleted tickets.
- Line 62: the visibility filter again. A ticket the user may not see returns `null`, and the service turns that into 404. We do not return 403, so users cannot even learn that the ticket exists.
- Line 63: `FirstOrDefaultAsync` returns the ticket or `null`.

### Part 3: visibility check, load for update, history

```csharp
        public Task<bool> IsVisibleAsync(Guid ticketId, Expression<Func<Ticket, bool>> filter, CancellationToken cancellationToken)
        {
            return db.Tickets
                .Where(t => t.Id == ticketId && !t.IsDeleted)
                .Where(filter)
                .AnyAsync(cancellationToken);
        }

        public Task<Ticket?> GetForUpdateAsync(Guid ticketId, Expression<Func<Ticket, bool>> filter, CancellationToken cancellationToken)
        {
            // Only what the workflow rules need: Team (leader check), Assignments, Responses (drafts)
            return db.Tickets
                .Include(t => t.Team)
                .Include(t => t.Assignments.Where(a => !a.IsDeleted))
                .Include(t => t.Responses.Where(r => !r.IsDeleted))
                .AsSplitQuery()
                .Where(t => t.Id == ticketId && !t.IsDeleted)
                .Where(filter)
                .FirstOrDefaultAsync(cancellationToken);
        }

        public async Task<IReadOnlyList<AuditLog>> GetAuditLogsAsync(Guid ticketId, CancellationToken cancellationToken)
        {
            return await db.AuditLogs
                .AsNoTracking()
                .Where(a => a.TicketId == ticketId)
                .OrderBy(a => a.CreatedAt)
                .ToListAsync(cancellationToken);
        }
    }
}
```

**Line by line:**
- Lines 66-72, `IsVisibleAsync`: used by the history endpoint to check "may this user see this ticket?" without loading it. `AnyAsync` becomes SQL `EXISTS`, which returns just true/false. There is no `AsNoTracking` because no entity is returned, so nothing is tracked.
- Note the filter can use navigation properties (for a leader, `t.Team.LeaderId`; for a member, `t.Assignments.Any(...)`). EF turns those into JOIN / `EXISTS` in SQL. `Include` is not needed for that; `Include` is only for filling properties in the result.
- Lines 74-85, `GetForUpdateAsync`: **no `AsNoTracking`**, on purpose. The workflow changes this ticket (status, team, manager) and then calls `SaveChangesAsync`. Because the entity is tracked, EF notices what changed and writes an `UPDATE` with only those columns. Tracking also keeps the original `RowVersion`, which EF puts in the `WHERE` for the concurrency check.
- Line 76, the comment: it loads only what the workflow rules need: `Team` (to check the caller is that team's leader), `Assignments` (to check the caller is assigned and avoid double-assigning), and `Responses` (to find the draft). Client, Manager and snapshot details are not needed.
- Line 83: the visibility filter here means a user cannot act on a ticket they cannot see. They get 404, the same as for a missing ticket.
- Lines 87-94, `GetAuditLogsAsync`: all audit rows for one ticket, oldest first, read-only. No visibility filter here: the service calls `IsVisibleAsync` first and filters which actions a client may see.

**Committee might ask:**
- *Why pass the filter in instead of writing the rule in the repository?* The visibility rule is business logic, so it belongs in Application (`TicketVisibility`), in one place. The repository only knows how to run it as SQL.
- *When do you use AsNoTracking?* For every read that just builds a DTO. Only `GetForUpdateAsync` is tracked, because only there do we change the entity and save it.
- *How does an EF exception become a 409?* The repository catches `DbUpdateConcurrencyException` and throws Application's `ConflictException`. `GlobalExceptionHandler` maps `ConflictException` to 409 with a ProblemDetails body.

```csharp
        public const string SectionName = "Jwt";
        public const string RoleClaimType = "role";

        // HMAC-SHA256 needs a key of at least 256 bits (32 bytes)
        private const int MinKeyBytes = 32;

        public string Issuer { get; set; } = string.Empty;
        public string Audience { get; set; } = string.Empty;
        public string SigningKey { get; set; } = string.Empty;
        public int ExpiryMinutes { get; set; } = 120;

        // Stop at startup with a clear message, instead of failing later on the first login
        public static JwtOptions Load(IConfiguration configuration)
        {
            var options = configuration.GetSection(SectionName).Get<JwtOptions>()
                ?? throw new InvalidOperationException($"Configuration section '{SectionName}' is missing.");

            if (string.IsNullOrWhiteSpace(options.Issuer) || string.IsNullOrWhiteSpace(options.Audience))
                throw new InvalidOperationException("Jwt:Issuer and Jwt:Audience must be set in appsettings.json.");

            if (Encoding.UTF8.GetByteCount(options.SigningKey) < MinKeyBytes)
                throw new InvalidOperationException(
                    $"Jwt:SigningKey must be at least {MinKeyBytes} bytes. Set it with: " +
                    "dotnet user-secrets set \"Jwt:SigningKey\" \"<key>\" --project TicketingSystem.API");

            if (options.ExpiryMinutes <= 0)
                throw new InvalidOperationException("Jwt:ExpiryMinutes must be greater than zero.");

            return options;
        }

        // One place builds the key, so signing and validating can't disagree
        public SymmetricSecurityKey CreateSigningKey() => new(Encoding.UTF8.GetBytes(SigningKey));
    }
}
```

**Line by line:**
- Line 10, `SectionName`: the config section name, written once.
- Line 11, `RoleClaimType = "role"`: the claim name that holds the user's role. `JwtTokenService` writes it, and `AuthExtensions` in the API tells JwtBearer to read roles from it. Sharing one constant means they cannot disagree.
- Line 14: HMAC-SHA256 needs at least a 256-bit (32-byte) key. A shorter key would be easy to brute-force, and the library rejects it anyway.
- Lines 16-19: the settings. `Issuer` (`Mizan.Api`), `Audience` (`Mizan.Web`) and `ExpiryMinutes` (120) are in `appsettings.json`. `SigningKey` is **not** in any tracked file. It comes from **user-secrets**, a file stored in the user's profile folder, outside the repo. `WebApplication.CreateBuilder` loads user-secrets automatically in Development (the API csproj has a `UserSecretsId`). On a new machine you set it once with `dotnet user-secrets set ...`.
- Line 24, `GetSection(SectionName).Get<JwtOptions>()`: **binding**. .NET reads the `Jwt` section from all config sources (appsettings, user-secrets, environment variables) and copies matching keys into a new `JwtOptions` object.
- Lines 27-36: checks that fail at startup with a helpful message: issuer and audience set, key at least 32 bytes (with the exact command to fix it), positive expiry.
- Line 42, `CreateSigningKey()`: a `SymmetricSecurityKey` is a key where the same secret both signs and checks the signature (HMAC). Signing (in `JwtTokenService`) and validating (in the API's `AuthExtensions`) both call this one method, so they always use the same bytes.

**About the options pattern:** the standard .NET options pattern binds a section to a class and injects it as `IOptions<T>`. This project uses a simpler version: `Load` binds and validates the section once, and `DependencyInjection.cs` registers the result as a plain singleton (`services.AddSingleton(JwtOptions.Load(configuration))`). Classes ask for `JwtOptions` directly, not `IOptions<JwtOptions>`. The reasons: validation runs right at startup, and `AddJwtAuth` in the API needs the values while services are still being registered, before DI can hand anything out.

Note: `Load` is called twice at startup, once in `AddInfrastructure` and once in `AddJwtAuth`. Both read the same configuration, so they get the same values.

**Committee might ask:**
- *Where is the JWT secret stored?* In user-secrets on the developer's machine, never in git. In production it would come from an environment variable or a secret store such as Azure Key Vault; the same binding code reads it.
- *What happens if the key is missing?* The app refuses to start and prints the exact `dotnet user-secrets set` command.

## [JwtTokenService.cs](../../TicketingSystem.Infrastructure/Auth/JwtTokenService.cs)

**What it is:** Implements `ITokenService`. After a successful login, it creates the signed JWT the client sends back on every request.

**The code:**

```csharp
using Microsoft.IdentityModel.JsonWebTokens;
using Microsoft.IdentityModel.Tokens;
using TicketingSystem.Application.Interfaces;
using TicketingSystem.Domain.Entities;

namespace TicketingSystem.Infrastructure.Auth
{
    public class JwtTokenService(JwtOptions options) : ITokenService
    {
        public (string Token, DateTime ExpiresAt) CreateToken(User user)
        {
            var expiresAt = DateTime.UtcNow.AddMinutes(options.ExpiryMinutes);

            var descriptor = new SecurityTokenDescriptor
            {
                Issuer = options.Issuer,
                Audience = options.Audience,
                Expires = expiresAt,
                SigningCredentials = new SigningCredentials(options.CreateSigningKey(), SecurityAlgorithms.HmacSha256),
                // The token is signed, not encrypted: anyone can read these, so no sensitive data here
                Claims = new Dictionary<string, object>
                {
                    [JwtRegisteredClaimNames.Sub] = user.Id.ToString(),
                    [JwtRegisteredClaimNames.Email] = user.Email,
                    [JwtOptions.RoleClaimType] = user.Role.ToString()
                }
            };

            return (new JsonWebTokenHandler().CreateToken(descriptor), expiresAt);
        }
    }
}
```

**Line by line:**
- Line 8: gets `JwtOptions` from DI through the primary constructor.
- Line 10: returns a **tuple**: the token string and its expiry time. The login response sends both, so the frontend knows when the token runs out.
- Line 12: expiry is now + 120 minutes (from config), in UTC.
- Line 14, `SecurityTokenDescriptor`: a description of the token we want: who issued it, who it is for, when it expires, how to sign it, and what claims it carries.
- Lines 16-17, `Issuer` and `Audience`: `iss` = "who made this token" (`Mizan.Api`), `aud` = "who it is for" (`Mizan.Web`). The API checks both, so a token made for another app is rejected.
- Line 18: becomes the `exp` claim. After this time the API rejects the token (with one minute of clock skew, set in `AuthExtensions`).
- Line 19, `SigningCredentials`: the key plus the algorithm (HMAC-SHA256). The signature proves the token was made by our server and was not changed. Change one character in the payload and the signature no longer matches.
- Line 20, the comment: a JWT is **signed, not encrypted**. Its header and payload are only Base64Url-encoded; anyone can paste it into jwt.io and read it. So we never put secrets (like the password hash) in it.
- Lines 21-26, **claims**: a claim is one fact about the user, stored as a name/value pair in the token.
  - `sub` (subject) = the user id. The API reads it to know who is calling.
  - `email` = the user's email.
  - `role` = the role as text, e.g. `"TeamLeader"`. `[Authorize(Roles = "Client")]` checks this.
- Line 29, `JsonWebTokenHandler().CreateToken(descriptor)`: `JsonWebTokenHandler` (from `Microsoft.IdentityModel.JsonWebTokens`) is the newer, faster replacement for `JwtSecurityTokenHandler`. It builds `header.payload.signature` and returns it as one string.

**What is inside the token:** three Base64Url parts separated by dots. The header (`alg: HS256`, `typ: JWT`), the payload (`sub`, `email`, `role`, `iss`, `aud`, `exp`, plus timestamps the handler adds by default), and the signature.

**Committee might ask:**
- *Can a user change their role in the token to "Admin"?* They can edit the text, but the signature would no longer match, and the API rejects it with 401. Only the server knows the signing key. Also, every ticket call reloads the user's role from the database.
- *Why is the role in the token if you reload it anyway?* `[Authorize(Roles = ...)]` on controllers needs it for a quick first check without a database call. The database reload is the second, authoritative check.

## [AuthService.cs](../../TicketingSystem.Infrastructure/Auth/AuthService.cs)

**What it is:** Implements `IAuthService`: checks email and password on login and returns a token, and loads the current user for `GET /api/auth/me`.

**The code:**

```csharp
using Microsoft.AspNetCore.Identity;
using Microsoft.EntityFrameworkCore;
using TicketingSystem.Application.DTOs.Auth;
using TicketingSystem.Application.Interfaces;
using TicketingSystem.Domain.Entities;
using TicketingSystem.Infrastructure.Persistence;

namespace TicketingSystem.Infrastructure.Auth
{
    public class AuthService(AppDbContext db, IPasswordHasher<User> passwordHasher, ITokenService tokenService) : IAuthService
    {
        // Only used to spend the same time on unknown emails as on real ones (see LoginAsync)
        private static readonly string DummyHash = new PasswordHasher<User>().HashPassword(new User(), Guid.NewGuid().ToString());

        public async Task<LoginResponse?> LoginAsync(LoginRequest request, CancellationToken cancellationToken)
        {
            // Soft-delete query filters aren't set up, so deleted users are excluded here by hand
            var user = await db.Users
                .AsNoTracking()
                .FirstOrDefaultAsync(u => u.Email == request.Email && u.IsActive && !u.IsDeleted, cancellationToken);

            if (user is null)
            {
                // Hashing is deliberately slow. Skipping it here would let an attacker
                // spot which emails exist just by timing the response.
                passwordHasher.VerifyHashedPassword(new User(), DummyHash, request.Password);
                return null;
            }

            var result = passwordHasher.VerifyHashedPassword(user, user.PasswordHash, request.Password);
            if (result == PasswordVerificationResult.Failed)
                return null;

            var (token, expiresAt) = tokenService.CreateToken(user);
            return new LoginResponse(token, expiresAt, ToDto(user));
        }

        public async Task<UserDto?> GetCurrentUserAsync(Guid userId, CancellationToken cancellationToken)
        {
            // Read from the database, not the token: a user deactivated after logging in is refused right away
            var user = await db.Users
                .AsNoTracking()
                .FirstOrDefaultAsync(u => u.Id == userId && u.IsActive && !u.IsDeleted, cancellationToken);

            return user is null ? null : ToDto(user);
        }

        private static UserDto ToDto(User user) => new(user.Id, user.Name, user.Email, user.Role.ToString());
    }
}
```

**Line by line:**
- Line 10: three dependencies, all injected as abstractions except the DbContext: the database, the password hasher (`IPasswordHasher<User>`), and the token service (`ITokenService`). Auth is simple enough that it uses `AppDbContext` directly instead of a repository. That is fine because `AuthService` itself lives in Infrastructure.
- Line 13, `DummyHash`: a hash of a random GUID, made once (it is `static readonly`) the first time `AuthService` is used. Nobody can log in with it; it exists only for the timing trick below.
- Lines 18-20: find the user by email, but only if active and not soft-deleted. Read-only (`AsNoTracking`), because login changes nothing.
- Lines 22-28, unknown email: we still run `VerifyHashedPassword` against the dummy hash and ignore the result. PBKDF2 is slow on purpose (many iterations). If we returned at once for unknown emails, a "wrong email" answer would come back much faster than a "wrong password" answer, and an attacker could measure that to find which emails have accounts. Doing the same slow work makes both cases take about the same time.
- Line 27 and line 32, `return null`: both "no such user" and "wrong password" return `null`. The controller turns that into the same 401 message, so the response never reveals which part was wrong.
- Line 30, `VerifyHashedPassword(user, user.PasswordHash, request.Password)`: reads the salt and settings out of the stored hash, hashes the typed password the same way, and compares.
- Line 31: `PasswordVerificationResult` has `Failed`, `Success`, and `SuccessRehashNeeded` (the password is right but was hashed with older settings). We only check for `Failed`, so both success values let the user in.
- Line 34: deconstructs the tuple from `CreateToken`.
- Line 35: returns a `LoginResponse` DTO (token, expiry, user info). Never the `User` entity, which contains the password hash.
- Lines 38-46, `GetCurrentUserAsync`: used by `/me`. The user id comes from the token's `sub` claim, but the user is read from the **database**. If an admin deactivated the user after they logged in, `/me` returns `null` → 401, even though the token itself is still valid.
- Line 48, `ToDto`: maps the entity to `UserDto`. The role is sent as text.

Note: when the result is `SuccessRehashNeeded`, the code does not save a new hash. That is normal for an MVP; a production system might upgrade the hash at that moment.

**Committee might ask:**
- *Why does a failed login with an unknown email still hash a password?* So both failure cases take the same time. Otherwise an attacker could find valid emails by measuring response times (a "timing attack" / user enumeration).
- *Why not say "email not found" to help the user?* Same reason: it would tell attackers which emails are registered. One generic message protects users.
- *What if a user is deactivated while they have a valid token?* `/me` and every ticket call reload the user from the database and refuse inactive users with 401. The token is not trusted for that.

## What happens on SaveChangesAsync

Example: the team leader assigns a member. `TicketWorkflowService` has loaded the ticket with `GetForUpdateAsync` (tracked), changed its `Status` to `InProgress`, and called `AddAssignment(...)` and `AddAuditLog(...)`. Then it calls `tickets.SaveChangesAsync(ct)`.

1. **Repository.** `TicketRepository.SaveChangesAsync` calls `db.SaveChangesAsync` inside a `try`.
2. **Change tracker.** EF compares each tracked entity with the snapshot it took when the entity was loaded. The `Ticket` is `Modified` (the `Status` changed). The new `TicketAssignment` and `AuditLog` are `Added`. Everything else is `Unchanged`.
3. **UpdatedAt stamp.** Our override in `AppDbContext` loops over `ChangeTracker.Entries<BaseEntity>()` and sets `UpdatedAt = DateTime.UtcNow` on the `Modified` ticket. The new rows keep `UpdatedAt = null`. `AuditLog` is skipped (not a `BaseEntity`).
4. **SQL in one transaction.** `base.SaveChangesAsync` opens a database transaction and sends:
   - `UPDATE Tickets SET Status = @p0, UpdatedAt = @p1 WHERE Id = @p2 AND RowVersion = @p3`, where `@p3` is the RowVersion we loaded. Only changed columns are in `SET`.
   - `INSERT INTO TicketAssignments (...)` and `INSERT INTO AuditLogs (...)`.
5. **RowVersion check.** SQL Server reports how many rows each statement affected.
   - **1 row** for the UPDATE: nobody else changed the ticket. SQL Server gives the ticket a new RowVersion, EF reads it back into the entity, the transaction **commits**, and all three changes are saved together.
   - **0 rows**: someone else saved this ticket after we loaded it, so the RowVersion no longer matched. EF **rolls back** the whole transaction (the assignment and audit row are not saved either) and throws `DbUpdateConcurrencyException`.
6. **409 mapping.** `TicketRepository` catches `DbUpdateConcurrencyException` and throws Application's `ConflictException("Someone else changed this ticket at the same time. Reload it and try again.")`. `GlobalExceptionHandler` in the API maps `ConflictException` to **409 Conflict** with a ProblemDetails body. The user reloads the ticket, sees the new state, and tries again if the action is still allowed.

Because the status change, the new rows and the audit entry are saved in **one** transaction, the audit log can never say something happened that did not, and a change can never be saved without its audit row.
